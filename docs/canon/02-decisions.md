# 02 · Рішення (ADR)

Формат: контекст → варіанти → рішення → ціна/наслідки → статус → джерела. Усі статуси - «прийнято» власником 22-23.08.2026, якщо не вказано інше. Джерела фактів - робочі дослідження `research-2026-08-22.md` (R) і `architecture-decision-2026-08-22.md` (D); вони лишились у робочій теці власника й у репозиторій не входять.

## ADR-001 · Варіант В (гібрид) замість А або Б

**Контекст.** А - усе на Free ($0); Б - Cloudflare Agents SDK + Anthropic API без VPS (≈ $28/міс при 8 запитах/добу, INFERRED). **Рішення.** В: ядро на Workers Paid, мозок на підписці Max на VPS, сторонні сервіси в квотах. **Ціна.** $5/міс; 2 точки деплою (обидві автоматичні); ризик політики підписки (ADR-002). **Чому не А:** 10 мс CPU, 5 кронів, Whisper WER 23 %, без Places. **Чому не Б:** суперечить пріоритету «лише підписка», дорожче в 5-10 разів.

## ADR-002 · Мозок лише на підписці; API-ключ-резерв не будуємо

**Контекст.** Anthropic 16.06.2026 призупинила окремий SDK-кредит (R, VERIFIED); `--bare` стане дефолтом `-p` і не читає OAuth (VERIFIED); docs Agent SDK: third-party developers - API key (VERIFIED). **Варіанти.** (а) тільки підписка; (б) + API-ключ із капом $5. **Рішення.** (а) - рішення власника R1. **Наслідки.** При зміні політики асистент зупиняється з алертом; план Б: `ANTHROPIC_API_KEY` у `.env` мозку + кап у консолі; оцінка $6-25/міс (INFERRED). Код мозку не має посилань на `--bare`; помилки 401/403/`usage-limit` класифікуються окремо й алертяться.

## ADR-003 · Ядро на Cloudflare Workers Paid

**Контекст.** Free: 10 мс CPU, 5 кронів, Browser Rendering 10 хв/добу, логи 3 дні (VERIFIED). **Рішення.** Paid $5: 30 с CPU, 250 кронів (не використовуються - ADR-004), Browser Rendering 10 год/міс, D1/DO/Workflows Paid-ліміти, логи 7 днів. **Ціна.** $5/міс - єдина нова витрата.

## ADR-004 · Один DO-планувальник замість Cron Triggers

**Контекст.** Чинний `*/5` крон з 10 задачами; 1 alarm на DO (VERIFIED); точність cron/alarm не задокументована (UNKNOWN). **Рішення.** `Scheduler DO` з таблицею `jobs` і alarm на найближчу; Cron Trigger лишається один (`*/5`) як сторож планувальника (якщо alarm не спрацював - тік з крону). **Ціна.** перенос `cron.mjs`; замір джитера на етапі 1.

## ADR-005 · Workflows для ланцюгів

**Контекст.** Кейси 1 і 5 - тижні очікування й кнопки. `waitForEvent` до 365 днів, події буферизуються, інстанси в очікуванні не рахуються в ліміт (VERIFIED). **Альтернатива.** стан у D1 + планувальник (ручна машина станів). **Рішення.** Workflows; стан дублюється в `chains.state_json` для Mini App і відновлення. **Ціна.** кроки $0.80/100k понад 500k/міс - непомітно.

## ADR-006 · D1 - система обліку; KV лишається для чинного стану

**Контекст.** KV без запитів; чек-ін у `stats` з CAS (`updateStats`). **Рішення.** Усе нове - у D1; KV не змінюється; мігрують лише `reminders`, `assistantPending`; `saved` і `settings` лишаються в KV, бо їх читає Mini App - це свідоме відхилення від відповіді Q10 («збережене і налаштування»): міграція дала б дві копії одних даних. Налаштування нового асистента живуть у `facts.setting.*`. Чек-ін не чіпається - записи через `recordEvent`. **Ціна.** два сховища; виправдано недоторканністю даних власника (00-vision §3.9).

## ADR-007 · Cloudflare Tunnel замість публічного порту

**Рішення.** `cloudflared` на VPS; Caddy/Let's Encrypt/ufw 443 прибрати; ядро кличе мозок через Access service token. **Ціна.** один процес на VPS; Zero Trust Free (50 місць - старе джерело, UNKNOWN на 2026, для одного власника неістотно).

## ADR-008 · Деплой мозку з GitHub Actions по SSH

**Рішення.** `deploy-host.yml` при push у `main` зі зміною `brain/**`: ssh deploy-ключем → `git checkout <sha>` → `npm ci --omit=dev` → `npm run build` (tsc, ADR-023) → `systemctl restart svitanok-brain` → перевірка `/health` (gitSha = sha). **Ціна.** deploy-ключ у GitHub Secrets, sudoers лише на restart одного юніта.

## ADR-009 · Без staging: розробка у проді під прапорцем (рішення власника 24.08)

**Контекст.** Власник не створює окремих секретів/бота/середовища для тестів і веде розробку одразу (24.08). Рекомендація staging (ADR-009 v1, 23.08) відкликана.
**Рішення.** Одне середовище (prod). Новий код деплоїться **вимкненим**: прапорець `ASSISTANT_V2` (plaintext var Worker: `off` | `shadow` | `on`). `off` - новий шлях не викликається; `shadow` - новий планувальник/ядро працюють паралельно зі старим, лише логують і не надсилають нічого (порівняння в `runs`); `on` - перемикання вебхука на новий шлях, старий хост вимикається. Мозок v2 ставиться на VPS поруч зі старим хостом (порт 8788, свій Tunnel hostname) і до `on` отримує лише `/health` і ручні smoke-запити. Резерв - git-тег `pre-redesign` + прапорець назад на `off`.
**Наслідки.** Приймальні чеклісти виконує власник у проді (свій бот, тема «Асистент») - кроки «у staging» у 03-plan читати як «у проді з прапорцем»; D1/DO/Workflows створюються в проді одразу (міграції лише додають таблиці, KV не змінюється до `on`); один набір секретів; Business-підключення і Mono-вебхук - лише після `on`. **Ризик (прийнято):** помилка в коді за прапорцем `on` зачіпає робочого асистента - відкат прапорцем займає секунди, але дані, записані новим шляхом у D1, лишаються (це не проблема - KV недоторканний).

## ADR-013 · Кейс 2: Business-підключення + експорт; MTProto відкладено

**Контекст.** Бот бачить лише приватні чати, лише нові повідомлення; Premium - суперечність джерел (VERIFIED/UNKNOWN); MTProto = повний доступ, «під наглядом» (VERIFIED). **Рішення.** Secretary mode з правами лише читання (без `can_read_messages`, без `can_reply`); історія/групи/канали - експорт JSON з Telegram Desktop → `InboxExport`. **Наслідки.** Ретенція 30 днів, дайджести назавжди, «забудь чат» T2. Перелік чатів - власник задасть пізніше.

## ADR-014 · Аналіз коду в GitHub Actions

**Контекст.** Ізоляція, наявний шаблон `brief.yml`, OAuth-токен у Secrets, 162 з 2 000 хв (VERIFIED). **Рішення.** `idea-analysis.yml`, read-only PAT на svitanok, portfolio, moviehouse, modern-blog; кеш за `head_sha`. **Ціна.** +1-2 хв старту раннера.

## ADR-015 · Рівні підтвердження визначає ядро (T0/T1/T2)

**Рішення.** Таблиця рівнів у `policy`; taint піднімає T0 → T1; мозок лише просить. T0 має «↩» 10 хв. **Наслідки.** Prompt injection не може записати назовні; кожна дія має тест рівня.

## ADR-016 · Інструкції лише з репозиторію, з хешем

**Контекст.** `instruction-files.md` (14.08) + уточнення D §4: KV не економить деплой, але потрібен через довжину. **Рішення.** `docs/assistant/**` → `sync-instructions.yml` → D1 `instructions` з хешем; тест парності; нема/розійшлось - прогін падає. Чат не пише інструкцій (може запропонувати diff). Персона й працівники - ті самі правила.

## ADR-017 · Колекції замість динамічних таблиць

**Рішення.** `collections` + `records` (JSON1), типи полів 07 §2; запити компілює ядро; Mini App - generic-екран (план). «Підвищення» до справжньої таблиці - окремим ADR за потреби.

## ADR-018 · Швидка смуга на Haiku 4.5 через той самий SDK

**Рішення.** Детермінований маршрутизатор + `quick` (1 хід, без інструментів) з `ESCALATE:`; помилка «тривіальне → повне» коштує лише часу. Gemini Flash-Lite і Workers AI LLM не використовуються для чату.

## ADR-020 · Памʼять: facts + сесії SDK + згортки + Vectorize

**Рішення.** Чотири шари (01 §2.1 `memory`); `assistantHistory` не мігрує. Ретенція: сесії 90 днів, згортки назавжди, `inferred`-факти з «↩». Ембединги - Workers AI (модель і якість для української - UNKNOWN, перевірка на етапі 2; резерв - без Vectorize, лише згортки в промпті).

## ADR-024 · Одна тема «Асистент» (+ DM); персона «Світанок»; команди

**Рішення.** Усі функції в одній темі; DM з ботом - той самий асистент (`thread_id = dm`), бо кнопка Mini App працює лише в приватному чаті. Персона з `persona.md`: «ти», трохи гумору, емодзі помірно, без мотивацій, без вигаданих чисел, спершу дія. Команди (07 §10): чинні лишаються як є (зокрема `/clear [N]` зберігає семантику «видалити N повідомлень»), нова `/new` завершує сесію треду, підказки `/idea /wish /money /inbox /status /forget` додаються (R26), але не обовʼязкові.

## ADR-025 · Rich Messages зі стрімінгом і статус-повідомленням

**Рішення.** `sendRichMessageDraft` для стрімінгу, `editMessageText` ≤ 1/с; fallback на звичайні повідомлення, якщо клієнт/метод недоступний (UNKNOWN підтримка на iOS-клієнті на момент етапу 2 - перевірка).

## ADR-026 · Брифінг лишається в GitHub Actions

**Рішення.** Не переносити (≈ 2 500 рядків, виграш лише «одна платформа»); переглянути після етапу 4. Dispatch/dead-man - через планувальник (перенос задач, не логіки брифінгу).

## ADR-029 · Фінанси: рівень мерчанта, правила «незвичного», категорії MCC

**Рішення.** Без позицій чека (VERIFIED відсутні у StatementItem); правила рахує ядро детерміновано: новий мерчант, > 1 000 грн, дубль за 5 хв, не UAH, підписка; «відхилення від звички» (3-тя кава за день) - відкладено до 2 місяців даних разом із бюджетами; категорії - 22 групи MCC (Oleksios, MIT) + `merchant_rules` власника; валюти в оригіналі + UAH за курсом Mono (`operationAmount`/`amount`). Працівник «Фінансист» лише відповідає на питання і пояснює вже обчислені прапорці - класифікацію не виконує. **Межа кейсу 4:** «недоцільність» = прапорці + доказ ціни за запитом, без оцінних суджень; для продуктових мереж (Сільпо/АТБ) порівняння цін неможливе без позицій чека - лише техніка/онлайн-товари з назвою від власника.

## ADR-036 · Етап 1, PR-1: уточнення схеми й порядку привʼязок (26.08)

**Контекст.** PR-1 за 03-plan мав нести «D1/DO/Workflows bindings», а 07 §1 містив дві дрібні суперечності, що виявились при написанні DDL. **Рішення.** (1) Привʼязка DO або Workflow без експортованого класу валить `wrangler deploy`, а деплой іде автоматично з main - тому PR-1 несе лише D1-привʼязку; DO-привʼязки їдуть у PR-2 (Scheduler) і PR-4 (RunRegistry) разом зі своїми класами, Workflows-привʼязки - на етапах, де зʼявляються класи (3+). Кінцевий стан етапу 1 ідентичний задуманому. (2) `quota_counters`: PK (key, period) замість key PK - ретенція «12 міс» вимагає рядка на місяць. (3) FTS5-таблиці отримують колонку `id UNINDEXED` - місток до TEXT-ключів базових таблиць, бо rowid FTS із ними не повʼязаний; таблиці standalone (не `content=`), синхронізація - код разом із записом. FTS5 на бойовій D1 VERIFIED 26.08 (проба з українським словом). **Наслідки.** 07 §1 оновлено; контракт-тест `tests/core-migrations.test.ts` тримає схему як дані й ловить розбіжності.

## ADR-040 · Голос: v:-callback-и, voice_pending у D1, shadow без префікса (28.08, етап 2 PR-4)

**Контекст.** 01 §3.3 і S-6-1..5 визначають потік (getFile ≤ 20 МБ → Deepgram nova-3 uk → «Я почув» ✅/✏️ → далі як текст; резерв Whisper з позначкою), але не визначають: (а) префікс callback-ів підтвердження (07 §9 знав лише p·c·r·a·u·m); (б) де живе транскрипт/file_id між «Я почув» і тапом (callback_data ≤ 64 байт не вміщає жодного); (в) як голос працює у shadow, де повний шлях гейтиться префіксом `v2:`, який не вимовиш. **Рішення.** (1) Новий kind `v` у 07 §9: `v:<id>:<choice>`, choice ∈ {ok, edit, go}; обробляє prerouter (не мозок). (2) Таблиця `voice_pending` (міграція 0009): id, kind transcript·file, text|file_id, duration_s, chat_id, thread_id, created_at; TTL 30 хв lazy (як proposals T1) + принагідна чистка при вставці; забирання тапом - claim через `DELETE…RETURNING` (подвійний тап → «Застаріло», не другий прогін). Аудіо, як і раніше, не зберігається ніде. (3) У shadow голос іде повним шляхом БЕЗ `v2:`: легасі голосові ніколи не обробляв (parseUpdate їх не читав), тож новий шлях нічого не краде, а прогін мозку стартує лише після явного тапу ✅ - сам тап і є гейтом. (4) Підтверджений ✅ транскрипт іде через той самий routeThreadText, що й текст власника, - включно зі «стоп» і класифікацією N3; транскрипт після ✅ вважається T0-входом власника (✅ - людська валідація), без `<external>`-маркування. (5) Квота deepgram_min (01 §7) рахується bumpQuota-ю після успішної відповіді Deepgram (хвилини спожиті навіть при тиші); резерв Whisper хвилин Deepgram не рахує. (6) Понад канон: `smart_format=true` у запиті Deepgram (пунктуація в «Я почув»; сирий потік слів нечитабельний) і стеля транскрипта 20 000 символів (як summary_md) зі зрізом по код-поїнтах. **Уточнення після ревʼю PR-4.** (а) Тап `v:` повертає тост ОДРАЗУ, а роботу (розпізнавання до 45 с, старт прогону до 10 с) віддає ядру через `defer` - вона виконується після `answerCallbackQuery` у тому ж `waitUntil`; інакше Telegram інвалідує callback_query і власник не бачить тосту взагалі. (б) Тап робить CAS-claim (`claimed_at`), а не видалення: ряд живе до ВІДОМОГО результату, і невдале «Розпізнати» повертає його в гру разом із живою кнопкою - інакше єдина копія file_id зникала б на першій мережевій невдачі. (в) TTL 5 хв, не 30: транскрипт - команда, чия дія залежить від моменту («стоп», підтверджений через півгодини, обірвав би вже інший прогін). (г) 401/403 від Deepgram - `misconfigured`, а не резерв: битий ключ мусить бути видимим, інакше роками віддавав би гірший Whisper при нульовому `deepgram_min`. (д) Резерв має власну стелю розміру (4 МБ): base64 для Whisper тримає буфер+рядок+base64 в одному ізоляті, і гілка обробки збоїв не сміє падати сама. (е) Стеля ПОКАЗУ (700 символів) окремо від стелі транскрипта: «Я почув» лишається одним повідомленням із кнопками, у прогін іде повний текст. (ж) У shadow «стоп» без префікса `v2:` перехоплюється, коли тред має що зупиняти - голос стартує прогони без префікса, тож і спиняти їх треба без нього.

**Ціна.** +1 міграція, ~300 рядків (voice.mjs + гілки prerouter). **Наслідки.** 07 §1 (+voice_pending) і §9 (+v) оновлено; сценарії S-6-1..5 закриті тестами PR-4; ogg/opus для Whisper-резерву - UNKNOWN до прод-проби (чеклист приймання). ⚠️ Міграція 0009 і код, що ЧИТАЄ `voice_pending`, їдуть у main одним PR, а деплой Worker'а робить Git-інтеграція Cloudflare повз Actions - перед мержем реліз-PR у main міграцію застосовує ВЛАСНИК (`wrangler d1 migrations apply svitanok --remote`), інакше перше голосове впаде на відсутній таблиці.

## ADR-039 · Prerouter: черга треду в RunRegistry DO, escalate-крок, /abort, shadow=v2: (27.08, етап 2 PR-3)

**Контекст.** 01 §2.1 вимагає thread-queue («один активний прогін на тред, друге повідомлення в чергу, "стоп" перериває»), 07 §5 - перезапуск chat після ESCALATE, S-0-3 - справжній abort, S-0-7 - ретраї при недоступному мозку; жоден канал цих механік не специфікований. **Рішення.** (1) Черга треду живе в RunRegistry DO (він уже серіалізує виклики): `threadClaim/threadFinish/threadClear/threadInfo`, стан {activeRunId, statusMessageId, queue[]}; глобальні слоти ≤2 НЕ дублюються в ядрі - їх тримає мозок (429 busy → повернення в чергу). (2) Канал ескалації - КРОК телеметрії: quick-прогін завершує /internal/runs кроком `{kind:'reply', name:'escalate', note:<оригінальний текст ≤120>, status_message_id}`; handleRuns ядра бачить його, редагує статус «думаю довше…» і стартує chat-прогін з тим самим текстом БЕЗ звільнення треду. /internal/runs тепер бойовий (PR-2), тож канал надійний у межах best-effort reportRuns мозку - при його збої страхує сторож (прогін закриється timeout-ом, статусник чесно скаже). (3) «стоп»: новий ендпоїнт мозку `POST /abort` {run_id} (підпис ADR-037, нонс) - сервер мозку тримає мапу runId→AbortController; reason='stop' НЕ робить deliver (тишу розриває ядро: «Зупинив.», черга очищена). (4) Shadow-режим (01 §5 уточнено): повідомлення з префіксом `v2:` іде НОВИМ шляхом повністю (чеклист на робочому боті), решта - класифікація N3 + рядок у runs (begin+finish, steps 0) і далі легасі. (5) Ретраї S-0-7: невдалий старт повертає запис у чергу (attempts+1, стеля 3); «підняття» черг - у складі 5-хвилинної задачі brain-health після зеленого handshake, без нового kind. **Ціна.** DO-методи + ~150 рядків prerouter; чесні заглушки callback-ів c:/r:/a:/m: до їхніх етапів. **Наслідки.** 07 §3 (+/abort), §10 (/new і R26 - реалізація) оновлено; сценарії S-0-2/3/7, S-N3-1..6 закриваються тестами PR-3.

## ADR-038 · Сесії та памʼять: /internal/session, профіль summarize, memory.search (27.08, етап 2 PR-2)

**Контекст.** 03-plan PR-2 вимагає resume за тредом, sessions у D1, згортку 04:00 і memory_chunks+Vectorize, але 07 не визначав: (а) як мозок повідомляє ядру sdk_session_id (його породжує SDK на VPS, а таблиця sessions - у D1 ядра); (б) хто і чим робить згортку (ядро без LLM); (в) яким інструментом модель шукає у згортках (S-N1-3). **Рішення.** (1) Тіло /run розширюється полем `session: {sdk_session_id, summary_md}` - ядро читає sessions перед викликом; мозок для chat робить resume і вставляє згортку в системний промпт. (2) Новий ендпоїнт `POST /internal/session` (підпис ADR-037): `{thread_id, sdk_session_id?, summary_md?, turns_inc?}` → upsert sessions; при summary_md ядро рахує ембединг (Workers AI bge-m3, 1024, cosine) і пише memory_chunks + Vectorize - єдиний шлях оновлення сесійного стану мозком. (3) Внутрішній профіль `summarize`: Haiku, без інструментів, 1 хід; вхід - транскрипт сесії, який мозок читає ЛОКАЛЬНО (SDK getSessionMessages, без resume - службовий хід не бруднить сесію); вихід - не deliver, а /internal/session. (4) Задача `memory-summarize` (вид уже в §7, 04:00): ядро кличе /run {profile:'summarize'} через новий клієнт ядро→мозок - перший бойовий викликач /run; у shadow - лише лог. (5) Інструмент читання `memory.search {q, limit?}` - НЕ taint (власні згортки): Vectorize topK → цитати згорток з датами. **Ціна.** +1 ендпоїнт, +1 профіль, +1 інструмент, Vectorize-індекс svitanok-memory. Якість bge-m3 для української - UNKNOWN (ADR-020): перевірка чеклистом приймання; резерв - згортки лише в промпті, memory.search чесно відмовляє без індексу.

## ADR-037 · Internal API: метод+шлях у підписі та nonce-антиреплей (27.08, етап 1 PR-5)

**Контекст.** 07 §3 визначав захист `/internal/*` як «Access + HMAC тіла + run_id + TTL 10 хв». Security-ревʼю PR-5 показало два класи атак у межах цього контракту: (1) підпис без методу/шляху переноситься між ендпоїнтами - підписаний `/internal/status` з тілом `{text}` проходить контракт `/internal/deliver`, і статусний рядок стає доставленим повідомленням; (2) без nonce той самий підписаний запит реплеїться необмежено в вікні ±10 хв (на етапі tools це повторні побічні ефекти). **Рішення.** Повідомлення підпису = `method\npath\nts\nrun_id\nnonce\nтіло` (розділювач \n однозначний); новий заголовок `X-Internal-Nonce`, споживається RunRegistry DO атомарно, памʼять 2×TTL, повтор = 401 replayed. **Ціна.** +1 заголовок і +1 RPC у гарячому шляху виклику інструмента (мікросекунди на запит). **Наслідки.** 07 §3 оновлено; мозок на етапі 2 підписує за цим контрактом; сценарій S-0-11 покривається тестами PR-5.

## ADR-035 · План дня v2: Денний працівник + детермінована розкладка в ядрі (погоджено 24.08)

**Контекст.** S-P-1…7 планують лише те, що вже в календарі; власник хоче вечірнє питання «що завтра», розкладку у вільні години без заповнення всього дня і уточнення. Перевірені практики: Айві Лі (≤ 6 пунктів, ввечері, перенос недоробленого) і тайм-блокінг із запасом і переоцінкою тривалості (джерела в `../proposal-day-plan-2026-08-24.md`). **Варіанти.** (а) усе в профілі `chat` - модель сама рахує вікна (нестабільно, не тестується); (б) автоплан з ідей/бажань без питання (асистент вигадує роботу); (в) ★ новий працівник «Денний» (розбір наміру, ≤ 2 уточнення, пояснення) + модуль `slots` у ядрі (вікна, ≤ 60 % заповнення, ≤ 3 глибокі блоки, × estimate_bias, енергія за чек-іном) + `DayPlanChain` (20:30 → 08:30 → 21:00). **Рішення.** (в). **Ціна.** ≈ 3 людино-дні в етапі 3; 1-2 Sonnet-прогони/день; таблиці `day_plans`, `plan_items`; без нових сервісів. **Наслідки.** Планувальник (поїздки) не змінюється; `daily-hint` не дублює план; блок «ДНІ» у тижневому звіті.
