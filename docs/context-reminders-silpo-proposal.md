# Пропозиція: контекстні нагадування та акції Сільпо

Дата: 05.10.2026. **Статус: дослідження й рекомендований дизайн.
Нові тригери, таблиці та конектор у цьому документі не реалізовано.**
Поточний код підтримує часові нагадування, план дня та загальний PriceTrack.

## 1. Нагадування від події, не від вгаданої години

### Шлях власника

1. «Нагадай після роботи заїхати в Сільпо».
2. Відповідь: «Нагадаю, коли завершиш роботу: заїхати в Сільпо».
   Кнопки: «Змінити», «Скасувати». Не питає точну годину без потреби.
3. Ще одна справа після роботи додається до того самого набору.
4. «Їду додому», «Закінчив працювати» або кнопка «Роботу завершено».
5. Якщо фраза однозначна для поточного робочого дня — зберігається подія
   завершення роботи й надсилається **одна** картка:
   «Перед дорогою додому: • заїхати в Сільпо; • забрати посилку».
6. Кнопки ведуть до конкретної справи: «Виконано», «Не зараз»,
   «На інший день», «Прибрати». «Не зараз» не потребує вгадувати годину,
   не означає виконання й не запускає нескінченні повтори.

Додавання до календаря й нагадування від події — різні операції.
Подія завершення роботи не повинна сама переносити весь вечір без згоди:
можна запропонувати перераховану чернетку, якщо фактичний час суттєво змінився.

### Розпізнавання та межі

| Ситуація                                           | Поведінка                                                                             |
| -------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Є поточна робоча зміна, «їду додому» зараз         | Подія завершення зміни й нагадування                                                  |
| Немає зрозумілої зміни або кілька контекстів       | «Роботу завершив?» — «Так», «Ні»                                                      |
| «Завтра поїду додому», «ще не їду», цитата         | Не запускати подію зараз                                                              |
| «Їду додому на перерву», потім повернення          | Не закривати зміну без уточнення                                                      |
| Робота закінчилась раніше/пізніше плану            | Фактична подія важливіша за планову годину                                            |
| Нічна зміна переходить через 00:00                 | Прив'язка до робочої зміни, не до дати повідомлення                                   |
| Поїздка/вихідний, просто повернення додому         | Не оголошувати робочий день завершеним                                                |
| Повторне повідомлення/другий тап                   | Не повторювати вже виданий набір                                                      |
| Додано нову справу після підтвердженого завершення | Показати нову справу одразу у чинному контексті або уточнити день; не дублювати старі |
| Немає прийнятого плану дня                         | Нагадування має працювати незалежно; уточнити scope, якщо потрібно                    |
| План закінчився, але власник нічого не повідомив   | Не стверджувати завершення; опційно запитати один раз                                 |
| Підтверджена голосова транскрипція                 | Той самий обробник, що для тексту                                                     |

Не кожне «їду додому» дорівнює «закінчив роботу». Модель може класифікувати
намір, але scope, збереження та запуск перевіряє ядро. Зовнішній лист,
цитата або чужий текст не мають права запускати персональну подію.

### Рекомендована реалізація

- Окремий тип event reminder, без фіктивного `due_at`. Залишити існуючі
  часові нагадування сумісними; реалізувати expand-міграцією.
- Сутність події: власник, робоча зміна/контекст, тип `work_finished`,
  фактичний час, підтверджене джерело й idempotency key.
- Сутність нагадування: текст, trigger, scope/shift, дата або режим
  «найближча зміна», строк актуальності, стан.
- Окремий журнал видачі та атомарний claim набору. Додавання нагадування
  й завершення роботи можуть прийти одночасно: потрібне узгодження,
  щоб нова справа не загубилась між зчитуванням списку й записом події.
- Transactional outbox доставляє картку; pending delivery переживає рестарт.
  Telegram — зовнішній сервіс: невизначений timeout не дає абсолютної
  гарантії exactly-once. Потрібен окремий стан uncertain delivery, а не
  безумовний повтор або помилкова позначка успішного надсилання.
- Стан «видано» відділений від «виконано». Після «Не зараз» справа
  лишається у важливому; подальший повтор лише за явним правилом.
- Для «після роботи» типовий scope — поточна/найближча зміна.
  «Щодня після роботи» — інший, явно повторюваний режим.
- Протерміновану справу не переносити на інший день мовчки.
- Картка редагується на місці після натискання, клавіатура відповідає стану,
  callback відразу має коротке підтвердження; старі кнопки безпечні.
- `/new` не стирає ці сутності. Export/backup/forget/retention і
  видимість у Mini App входять у той самий реліз.
- Часовий fallback дозволяється лише як окремо погоджена опція.
  Плановий кінець роботи не є доказом фактичного завершення.

### Acceptance

Перевірити: без плану; ранній/пізній вихід; нічну зміну; кілька справ;
дублікати webhook; одночасне додавання і trigger; рестарт; збій доставки;
старі кнопки; заборонені/майбутні фрази; чужий текст; голос; `/new`;
скасування, пропуск і виконання окремо; privacy/export/restore.

## 2. Улюблені продукти й акції Сільпо

### Що підтвердило дослідження

Офіційна документація описує MCP із OAuth, пошуком товарів, акціями
магазину, улюбленими товарами та персональними пропозиціями. Пошук/акції
потребують контексту кошика; точні аргументи слід перевірити після входу.
[Документація Сільпо](https://ai-factory.silpo.ua/docs/mcp).

Сервіс представлено для хакатону. Опублікована оферта задає період
01.08–30.09.2026; це **не доказ** доступності щоденної production-інтеграції
після завершення. Потрібно уточнити доступ і ліміти у підтримки
`mcp@silpo.club`, не реєструвати користувача на хакатон автоматично.
[Оферта](https://ai-factory.silpo.ua/terms).

### Перед реалізацією

1. Перевірити доступ звичайного акаунту й дозволене фонове використання.
2. Авторизацію проходить власник. Світанок не запитує пароль/OTP у чаті.
3. Вибрати магазин і канал покупки. Онлайн-ціна не оголошується ціною
   фізичного магазину без перевірки; персональний купон — окрема умова.
4. Перевірити, чи каталог доступний read-only із наявним контекстом.
   Якщо треба створити/змінити кошик для контексту — це окремий явний дозвіл,
   не прихований крок «перевірки ціни».
5. За відсутності дозволеного доступу не заміняти інтеграцію обходом
   авторизації, закритим мобільним API чи агресивним scraping.

### UX і власна таблиця

«Стеж за акціями на цей сир» → результати пошуку → вибір **конкретного**
товару, бренду й фасування → магазин → правило сповіщення.

Таблиця в Mini App:

| Поле                             | Призначення                                 |
| -------------------------------- | ------------------------------------------- |
| Назва, бренд, фасування          | Не плутати різні варіанти                   |
| SKU/product ID і посилання       | Однозначне джерело                          |
| Магазин і канал                  | Область ціни/наявності                      |
| Поріг ціни або відсотка          | Коли повідомляти                            |
| Поточна/звичайна ціна            | Порівняння; лише якщо джерело справді надає |
| Умови/кінець акції               | Купон, картка, кількість, строк             |
| Перевірено о…, наявність, статус | Чесна свіжість даних                        |
| Увімкнено / пауза                | Керування моніторингом                      |

Рекомендовані нові прикладні сутності:
`grocery_watch_items` — список і правила,
`grocery_price_observations` — історія,
`grocery_alerts` — dedupe й доставка.
Це пропозиція назв, **не наявні таблиці**.
Не класти всю історію цін у персональні `facts`; там доречна лише
перевага магазину чи правило сповіщення.

### Щоденна перевірка

- Один пакетний job на день для активних товарів у вибраному контексті.
  Вартість/знижку читає адаптер; щоденний LLM-пошук кожного товару не потрібний.
- Лише allowlisted read tools; кошик, замовлення й оплата не є доступними
  діями моніторингу. Token — серверний, поза prompt/logs/фронтендом/звичайними facts.
- Сповіщати про нову релевантну акцію або суттєву зміну її умов, не
  щодня про той самий незмінний deal. Нові акції об'єднувати в одну картку.
- Помилка, відсутність або невідома ціна не означають «знижок немає»
  чи «ціна нуль». Показувати останню успішну перевірку й стан доступу.
- Retry/backoff, ліміти, перерваний OAuth, неповна пачка та відсутній товар
  мають окремі стани. Не генерувати помилкові відсотки без базової ціни.
- Кнопки: «Відкрити товар», «До покупок», «Пауза».
  «До покупок» — локальний список, не непомітна зміна кошика Сільпо.
- Набір «після роботи» може показувати вже перевірені акції зі списку покупок,
  але не змішувати «купити» з «знижка є» і не додавати покупки без згоди.

### Порядок впровадження

1. Спочатку контекстні нагадування, незалежно від Сільпо.
2. Окремий read-only spike: доступ, магазин, точний товар, ціна й умови.
3. Після підтвердження джерела — favorites/watchlist, щоденний job,
   пакетні сповіщення, privacy й acceptance.
4. Після стабільного моніторингу — зручне поєднання зі списком покупок
   і нагадуваннями після роботи.
