# Сільпо: результат read-only перевірки

Перевірено **05.10.2026, 17:39:16 UTC**. Публічне підключення працює.
**Авторизований каталог, ціни та щоденний моніторинг ще не перевірені й не ввімкнені.**
Production, D1, Telegram, кошик і акаунт власника не змінювалися.

## Що перевірено наживо

| Запит GET до `https://mcp.silpo.ua`         | Результат                                                                                                      |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `/mcp` без токена                           | 401, Bearer challenge з URL метаданих ресурсу                                                                  |
| `/.well-known/oauth-protected-resource/mcp` | 200; ресурс `/mcp`, сервер авторизації цього ж origin, Bearer у заголовку                                      |
| `/.well-known/oauth-authorization-server`   | 200; issuer цього ж origin, `/authorize`, `/token`, `/register`, PKCE S256, authorization code і refresh token |

`scopes_supported` у перевірених метаданих не опубліковані. Це **не** означає
ані доступ без входу, ані наявність серверного read-only scope.
`refresh_token` у переліку grant types не підтверджує фактичний строк доступу
або видачу refresh token конкретному клієнту.

Відтворення з кореня репозиторію, Node >=20:

```powershell
node scripts/silpo-preflight.mjs
npx vitest run tests/silpo-preflight.test.ts
```

Скрипт використовує лише три фіксовані публічні URL і GET. Не читає env чи
секрети, не надсилає cookies/токени, не переходить за redirects, не реєструє
OAuth-клієнта, не викликає tools. Таймаут — 10 секунд на запит; JSON обмежений
32 KiB; після невдалої перевірки зупиняється без retry. Виводить лише етап,
HTTP-статус і власний код результату, не відповідь сервера чи текст помилки.
Імпорт модуля не запускає мережу. Exit 0 означає **лише успішний discovery**,
а не готовність каталогу. Зміна очікуваних URL/метаданих потребує перегляду,
не автоматичного прийняття нового сервера. Це діагностика, не OAuth/MCP-клієнт.

## Документовані можливості та невідомі умови

[Офіційна MCP-документація](https://ai-factory.silpo.ua/docs/mcp) описує
OAuth, каталог, пошук, акції магазину та улюблені товари. Точні схеми аргументів
отримуються через авторизований `tools/list`; публічний опис не замінює їх.
Пошук і акції потребують контексту кошика: магазин, канал та валідний слот.

[Оферта](https://ai-factory.silpo.ua/terms) описує хакатон 01.08–30.09.2026.
Завершення хакатону **не означає вимкнення сервера** — він відповів сьогодні.
Але публічні матеріали не підтверджують умови приватного постійного моніторингу
поза хакатоном. Не реєструємо власника учасником і не приймаємо оферту за нього.

Невідомі: доступ звичайного акаунту після хакатону, дозволені фонові запити,
числові квоти, токен/refresh lifecycle, правила збереження історії цін і
відповідність онлайн-ціни ціні фізичного магазину. Наявність endpoint не
закриває цих питань. Пошук готового Silpo-плагіна у доступному каталозі не
дав результатів; це не доказ відсутності інтеграцій в інших каталогах.

## Межі майбутнього конектора

Перший режим — лише звичайні акції вибраного магазину й конкретних товарів.
Серверний allowlist (після звірення `tools/list`):

- `silpo_list_branches`, `silpo_get_time_slots`;
- `silpo_get_my_shopping_cart`, `silpo_get_shopping_cart_by_id` — лише щоб
  отримати й перевірити контекст **наявного** кошика;
- `silpo_find_products_batch`, `silpo_get_products`, `silpo_get_product_details`;
- `silpo_get_promotions`;
- `silpo_get_my_favorites` — лише за окремим вибором імпорту улюблених.

Поки не підтверджено схеми, це **список дозволених назв, не реалізовані виклики**.
Необхідність інших read tools оцінюється після перевірки схеми, не розширює
allowlist автоматично. Персональні купони — окреме майбутнє підключення зі згодою.
Обмеження контролює код конектора, не prompt і не твердження моделі; клієнтський
allowlist не звужує права самого OAuth-токена на стороні Сільпо.

Заборонені моніторингу: створення/оновлення/очищення кошика, зміна товарів,
улюблених, сертифікатів, бонусів; замовлення й оплата. Не читати профіль,
родину, збережені адреси, чеки й історію замовлень. Відповідь наявного кошика
може містити зайве: виділяти тільки потрібний контекст у пам'яті процесу,
не зберігати/логувати весь payload і не передавати його моделі.

Якщо кошика/слота немає або він непридатний — `needs_cart_context`, а не
непомітне створення чи оновлення. Не резервуємо доставку щодня заради цін.
Якщо Сільпо вимагає змінювати кошик для кожної перевірки, поточний read-only
варіант не проходить приймання: потрібен інший дозволений шлях від провайдера.

Вхід власник проходить на офіційній сторінці; пароль і OTP не надсилаються
асистенту. Майбутній OAuth-клієнт потребує PKCE S256, одноразового state,
точного redirect URI, перевірки issuer і захисту від повторного callback.
Токени — лише серверно, шифровані й відділені від facts, prompt, логів,
Mini App і звичайного експорту. Refresh — single-flight, без паралельного
використання старого токена; відкликання/видалення зупиняє scheduler.
Ці механізми **ще не реалізовані цим spike**.

## Приймання перед ввімкненням щоденної перевірки

1. Підтвердити дозволений персональний доступ і квоти в підтримки.
2. Власник входить; перевірити `tools/list` і фактичні read-only схеми.
3. Вибрати магазин/канал, перевірити існуючий контекст без writes.
4. На одному точному SKU перевірити назву, бренд, фасування/одиницю,
   ціну UAH, наявність, акцію та її умови. Не підміняти фасування схожим товаром.
5. Звірити з офіційною сторінкою того самого товару в тому самому контексті.
   Онлайн-ціну не обіцяти для покупки офлайн без підтвердження джерела.
6. Тільки після цього реалізувати watchlist/observations/alerts, privacy,
   retention, export/forget і один денний job. Назви полів власного DTO не
   оголошувати схемою Сільпо; відсутня базова ціна не дозволяє вигадувати %.
7. Протестувати expired/revoked token, 403, 429 із backoff, прострочений слот,
   зміну магазину, неповну пачку, відсутній SKU, дедуплікацію повідомлень.

Стани конектора: `needs_login`, `access_denied`, `needs_cart_context`,
`rate_limited`, `temporarily_unavailable`, `stale`, `ready`.
Помилка не дорівнює «знижок немає». Показувати останню успішну перевірку;
не розсилати незмінний deal щодня. Пауза вимикає перевірки, відключення
видаляє credential. Не замінювати закритий доступ обходом авторизації.
