# Персональні дані: backup/export/forget/restore

Дата: 05.10.2026. Статус: реалізація; production-реліз потребує окремої
перевірки. Нова SQL-міграція не потрібна: використовуються наявні таблиці.

## Зміни

- Knowledge documents/versions/chunks, learning sessions і worker card actions
  включені до спільного lifecycle.
- Контракт охоплення читає всі міграції, не ручний піднабір.
- Старий архів не очищує нові таблиці, яких не містить. Explicit empty очищує.
- Неповний або пошкоджений knowledge-набір відхиляється до виконання SQL.
- Активна ready-база знань після restore стає pending й індексується з D1.
  Revoked-документи не перетворюються на active.
- Повне forget видаляє обидві векторні проєкції до локальних джерел,
  включно зі stable knowledge IDs без записаного vector_id.
- D1 очищується одним транзакційним batch; зовнішній або локальний збій
  не оголошується completed. KV/DO cleanup залишається окремим етапом.

## Локальні перевірки

`tests/personal-data-lifecycle.test.ts`: export і redaction; шифрований
round-trip; пошук недоступний до reindex та доступний після нього; старий
архів поверх нових даних; explicit empty; malformed/partial archive;
порядок vector → D1; Vectorize failure/retry; відсутній binding;
пагінація понад 2000 chunks; rollback локального batch після пізнього збою.

`tests/restore-drill.test.ts` містить synthetic knowledge, learning та
worker-card rows і перевіряє clean restore актуальної схеми. Жодних
production-документів, секретів чи платних API-викликів для цього не потрібно.

## Реліз

1. Перевірити наявність усіх міграцій у цільовій D1 read-only. Не виконувати
   код проти старої схеми й не підміняти відсутні таблиці мовчазним пропуском.
2. Пройти повні test/typecheck/lint/format gates. Зберегти rollback reference.
3. Перед push перевірити Cloudflare deployment settings: робоча гілка може
   активувати production. Не змінювати систему деплою в цьому зрізі.
4. Публікувати звичним погодженим шляхом; перевірити SHA Worker, CI та `/ready`.
   Brain runtime й модельні інструкції цим виправленням не змінюються.
5. Наступний реальний backup має включити нові таблиці. Старі backup-файли
   не дописуються. Restore старого backup не поверне дані, яких у ньому не було.
6. Реальний clean restore drill робити лише на ізольованій локальній базі.
   Синтетичний drill не є доказом справності конкретного production-архіву.

## Безпечний живий чек-ін

- `/ready`: система доступна, стан backup без хибного «готово».
- Після погодженого експорту перевірити файли п'яти таблиць у ZIP; порожній
  масив допустимий, якщо модуль не використовувався.
- **Не запускати `/forget` → «Усе» для тестування на реальних даних.**
  Повне видалення та fault injection перевіряються лише на synthetic fixture.
- Не виконувати remote restore заради smoke-тесту.

Дані Сільпо й контекстні нагадування цим зрізом не додаються.
