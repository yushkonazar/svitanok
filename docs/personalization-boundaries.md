# Персоналізація: перший захисний етап

Реалізовано локально 11.10.2026, після production-релізу #469.
Це не ввімкнення нового збору даних, не fine-tuning і не готовий повний
адаптивний асистент. Чинні інтеграції й дані production не змінювалися.

## Що виправлено

- Нові модельні записи profile/habit/contact/place/vehicle/inferred потребують
  погодження. До рішення вони лишаються proposals, не активними facts.
  Рішення власника робить підтверджений персональний запис owner_assertion.
- Низькорівневий writer не дозволяє actor=model приписати слова власнику
  або перезаписати чинний owner_assertion. Модель не керує actor через payload.
- Наявний policy-захист підсилено на момент запису: старий дозвіл не може
  замінити факт, який уже змінився після формування картки.
- Незмінний ID останньої ledger-події є write token. Час і значення самі
  недостатні: видалення/повторне створення або однакові timestamps теж виявляються.
  Токен ядро передає окремо від model payload, зберігає у proposal context.
- Current truth і ledger пишуться в атомарному D1 batch. Ledger insert
  залежить від фактичного запису; програна гонка не створює фальшивої історії.
- Видалення й відкат теж перевіряють токен. Стара кнопка не стирає новіше
  рішення. Для старих карток без токена потрібен новий запит, не здогад стану.
- Збій fact proposal/undo не залишається статусом approved: повторний тап
  не відповідає успіхом. Конфлікт повідомляється людською мовою.
- Routine settings зберігають чинний шлях. Це не нова семантична класифікація
  всіх довільних setting-ключів і не дозвіл робити з них приховані звички.

Міграції не потрібні: використано facts, fact_ledger і proposal context.
У production критично зберігати transactional D1 batch. Старі local stubs
без batch не доводять конкурентну безпеку; для таких тестів увімкнено
atomicBatch у SQLite shim або використано окремий транзакційний adapter.

## Межі й наступний етап

Автоматичне збереження явних вподобань без зайвих питань ще потребує
контракту first-party evidence: ядро має відрізняти твою фразу від цитати,
заперечення, умовного прикладу, транскрипції та чужого листа. Рядок source
від моделі не є достатнім доказом. Захист не послаблюється заради зручності.

Наступне: режими пам’яті й allowlist категорій у налаштуваннях, перегляд
фактів/пропозицій, виправлення одним спільним контрактом, дозволені
спостереження з фактичних дій. Новий аналіз пошти/каналів, добірки дозвілля,
строки спостережень і вартість погоджуються окремо. Геолокація та iOS
залишаються відкладеними. Інструкції працівників не змінюються моделлю.

## Перевірки

Фінальний локальний прогін: 5377 серверних і 297 Mini App тестів, перевірка
типів, lint обох частин, format check та production build Mini App.

Нові 15 тестів policy: шість класів кандидата, відмова, два різні погодження,
підроблений payload token, стара картка, застаріле видалення, захист writer,
однакові timestamps і recreate, старий undo, rollback після збою ledger.
Додатково перевірені повторні натискання після конфлікту та конкурентні
перші записи з реальним транзакційним SQLite batch.

Живе приймання лише після окремого релізу цього етапу:

1. «Запам’ятай: зазвичай починаю роботу о 09:00». Погодити й перечитати факт.
2. «Зазвичай о 10:00» - отримати нову пропозицію. Змінити факт іншим
   підтвердженим запитом, тоді натиснути стару картку: новіше значення зберігається.
3. Відхилити пропозицію нової звички: вона не з’являється у поточних фактах.
4. Повторити кнопку після конфлікту: немає повідомлення про виконану зміну.

Перевіряти без надсилання секретів і без змін реальних фінансових операцій.
