# Персоналізація: захист, явні факти та керування пам’яттю

Реалізовано локально 11.10.2026, після production-релізу #469.
Це не fine-tuning і не готовий повний адаптивний асистент. За замовчуванням
персональні записи потребують підтвердження. Автоматичний режим вмикається
лише окремим вибором категорій власником. Чинні інтеграції й дані production
не змінювалися; цей блок ще не опублікований.

## Що виправлено

- Нові модельні записи profile/habit/contact/place/vehicle/inferred потребують
  погодження. До рішення вони лишаються proposals, не активними facts.
  Рішення власника робить підтверджений персональний запис owner_assertion.
- Низькорівневий writer не дозволяє actor=model приписати слова власнику
  або перезаписати чинний owner_assertion. Модель не керує actor через payload.
- Наявний policy-захист підсилено на момент запису: старий дозвіл не може
  замінити факт, який уже змінився після формування картки.
- Незмінний ID останньої ledger-події є write token. Час і значення самі
  недостатні: видалення/повторне створення або однакові timestamps теж виявляються.
  Токен ядро передає окремо від model payload, зберігає у proposal context.
- Current truth і ledger пишуться в атомарному D1 batch. Ledger insert
  залежить від фактичного запису; програна гонка не створює фальшивої історії.
- Видалення й відкат теж перевіряють токен. Стара кнопка не стирає новіше
  рішення. Для старих карток без токена потрібен новий запит, не здогад стану.
- Збій fact proposal/undo не залишається статусом approved: повторний тап
  не відповідає успіхом. Конфлікт повідомляється людською мовою.
- Routine settings зберігають чинний шлях. Це не нова семантична класифікація
  всіх довільних setting-ключів і не дозвіл робити з них приховані звички.

Для першого захисного етапу міграції не потрібні: використано facts,
fact_ledger і proposal context. Для походження голосу додано expand-міграцію
`0038_voice_owner_evidence.sql`, ще не застосовану в production.
У production критично зберігати transactional D1 batch. Старі local stubs
без batch не доводять конкурентну безпеку; для таких тестів увімкнено
atomicBatch у SQLite shim або використано окремий транзакційний adapter.

## Режими й явні факти

Mini App → Налаштування → Пам’ять асистента. Прямий start parameter:
`memory`, локальний маршрут `/settings?panel=memory`. Нової вкладки немає.

- **Питати перед записом** — початковий режим; модельні кандидати потребують
  погодження, а невідомий/непідтверджений/прострочений режим не дає auto-consent.
- **Явні факти автоматично** — власник обирає вподобання, звичні часи дня
  та/або стиль відповідей і натискає «Зберегти режим». Саме перемикання
  поля ще нічого не змінює. Настройка зберігається в `facts.setting.personalization`.

Без LLM розпізнається вузький однозначний набір: «Люблю азійську кухню»,
«Не люблю піцу», «Зазвичай прокидаюся о 08:00», «Зазвичай обідаю о 13:00»,
«Зазвичай лягаю спати о 23:00», «Відповідай коротко/детально/стисло/українською».
Допускається префікс «Запам’ятай:». Вподобання мають стабільний ключ за
нормалізованим предметом: заперечення змінює ставлення, а не створює дубль.

Цитати, умовні приклади, тимчасові плани, URL, неоднозначні речення й
непідтримувані формулювання лишаються на звичайному шляху з policy.
Відповідь на поточне питання сценарію не перехоплюється як окремий факт.
Явна команда «Запам’ятай:» або «Відповідай…» може бути окремою інструкцією.

Походження встановлює Telegram-парсер, не модель: основний власник,
оригінальне повідомлення з ID, без forward/quote/via-bot/delegated source.
Для голосу потрібні прапорець початкового повідомлення й погоджений
транскрипт. Старі pending rows мають `owner_composed=0`; без нової колонки
голос продовжує працювати, але не дає автоматичного запису. Це не біометрія:
копіювання чужого речення без маркерів цитати неможливо безпомилково розпізнати.

Поточний consent token повторно звіряється в атомарному записі. Вимкнення
режиму зупиняє відкладену зміну; same-value повтор не створює нову ledger-подію.
Є людське підтвердження й відкат. Для голосу результат і кнопка змінюють
початкову картку, не лишаючи поруч незавершене «Починаю обробку».

## Перегляд і виправлення

`GET/POST /api/memory` доступний лише основному власнику через підписаний
Telegram initData, `private, no-store`. Публічне демо не читає й не змінює
пам’ять. Екран завантажується за потреби: 25 фактів на сторінку й до 50
активних T1 пропозицій. Показує джерело, актуальність і безпечне значення;
не повертає приватні setting-ключі, run inputs, prompts чи повну історію.

Зміна й прибирання проходять той самий guarded fact writer і ledger, що й чат.
Редактор бере токен початкового запису; фонове оновлення не стирає чернетку.
Застаріла чернетка потребує перегляду. Прибирання потребує окремого
підтвердження й прибирає лише поточний факт: історія лишається до `/forget`.
Для складених записів редагування — через чат; у стандартному вподобанні
можна змінити ставлення, але не підмінити предмет під старим ключем.

Окремий вибір актуальності очищає попередні review/expiry дати. Часи звичок
перевіряються як HH:mm. Старі/закриті пропозиції не виконують нову дію.
Після мережевого збою запис не повторюється автоматично: спершу оновлення
пам’яті. Підтверджений запис із невдалим snapshot показується саме так,
а не видається за незбережений факт. Впізнавані паролі/ключі/коди блокуються;
це не універсальний детектор секретів, тому їх не слід надсилати асистенту.

## Межі й наступний етап

Новий аналіз пошти/каналів, добірки дозвілля, дозволені спостереження з
фактичних дій, їхні строки й вартість погоджуються окремо. Цей режим не
вмикає нові джерела чи розсилки. Геолокація та iOS залишаються відкладеними.
Інструкції працівників не змінюються моделлю. Платіж не є доказом відвідування.
Наявність факту не гарантує, що кожний працівник правильно використає його:
якість планування й персональних рекомендацій потребує окремих evals.

## Перевірки

Фінальний локальний прогін: 5431 серверний і 313 Mini App тестів, перевірка
типів, lint обох частин, format check та production build Mini App.

Нові 15 тестів policy: шість класів кандидата, відмова, два різні погодження,
підроблений payload token, стара картка, застаріле видалення, захист writer,
однакові timestamps і recreate, старий undo, rollback після збою ledger.
Додатково перевірені повторні натискання після конфлікту та конкурентні
перші записи з реальним транзакційним SQLite batch. 53 тести workspace/consent/
API/voice та 16 UI/client тестів перевіряють першоджерело, відмову від режиму
під час запису, privacy, CAS, редагування, мережеву невизначеність і демо.

Живе приймання лише після окремого релізу цього етапу:

1. У початковому режимі: «Запам’ятай: люблю азійську кухню». Погодити або
   відхилити; перечитати результат у пам’яті Mini App.
2. Увімкнути auto лише для вподобань. «Люблю піцу» — людське підтвердження
   без окремого погодження. Повтор — «Це вже пам’ятаю» без дубля.
3. «Не люблю піцу» — той самий факт з іншим ставленням; перевірити відкат.
4. «Завтра обідаю о 14:00» — не нова постійна звичка. Переслати чужу
   «Люблю суші»: вона не має автоматично стати твоїм уподобанням.
5. Голосом «Люблю піцу», погодити транскрипт. Результат з відкатом у тій
   самій картці; повторний тап не створює другу дію.
6. Увімкнути schedule: «Зазвичай прокидаюся о 08:00». Відкрити редактор,
   змінити факт через чат на 09:00, оновити екран: стара чернетка не записується.
7. Прибрати тестовий факт у Mini App; відмова залишає його, підтвердження
   прибирає current entry. Історія при цьому не оголошується стертою.
8. Вимкнути auto. Новий факт знову потребує погодження; `/new` не стирає
   ні фактів, ні обраного режиму.

Ці дії можуть змінювати звички планувальника. Використовуй свої справжні
значення або заздалегідь запиши їх і поверни після перевірки.

Перевіряти без надсилання секретів і без змін реальних фінансових операцій.
