# Подорожі: покроковий сценарій

Основне планування проходить у Mini App; Telegram супроводжує вже створену подорож відповідно до вибраного режиму. Замість великої форми головний екран показує одне актуальне питання. Відповіді зберігаються одразу; необов’язкові можна відкласти, попередні — уточнити перед підтвердженням.

Стан: реалізація для 0.21.0 підготовлена локально; цей документ не підтверджує публікацію в продакшені.

## Шлях користувача

1. Місце → походження → дати й значення повернення → транспорт.
2. Окремо люди в дорозі, загалом на місці, для проживання й назад; діти та вік, якщо потрібні.
3. Час виїзду, квитки, багаж; дати проживання, розміщення й кількість номерів; бюджет і на кого він; інтереси, темп, їжа та доступність.
4. Перевірка брифу. «Підтвердити й знайти транспорт» починає перший пошук. Країна й IANA-пояси визначаються наявним географічним модулем; питання залишаються для невідомих чи неоднозначних місць.
5. Транспорт → житло → місця. Пошук наступного кроку отримує параметри й фактично обрані попередні варіанти. Для дороги туди й назад транспортна пропозиція описує обидва напрямки. Власний варіант і відкладене рішення дозволені явно. До плану можна додати кілька місць.
6. «Перейти до підготовки» створює спільний простір подорожі й списки справ. Вибір варіанта не підтверджує придбання чи бронювання.
7. Підготовка → дорога → на місці → повернення → справи після подорожі. Перегляд етапу не змінює фактичний стан; його підтверджують окремі кнопки власника.

Підготовка має розділи документів, квитків/бронювань, речей, дому й повернення. Речі мають окремі чекбокси; є власні пункти та «не потрібно». Доповнення шаблоном зберігає власні назви й виконані справи. У дорозі доступні обраний транспорт, житло, детальний маршрут і офлайн-копія. На місці — обрані заняття, відвідані місця, журнал і витрати. Після підтвердженого повернення — справи із заставами, розрахунками, речами й враженнями.

## Збереження й пошук

- `trip_briefs.answers_json._planning`: ревізія планування, підтверджений бриф, рішення та стан пошуку. Нові таблиці чи міграції не потрібні.
- Кожний пошук має зареєстрований `run_id`. Повторний тап повертає той самий активний пошук. Пошук виконується окремим профілем `trip-research`, без інструментів запису, історії основного чату й Telegram-доставки результату.
- Підписаний `/internal/runs` приймає результат лише відповідного зареєстрованого профілю й активного запиту. Прострочені, замінені та несумісні з новим брифом результати не застосовуються. Повтор completion може завершити невдалий запис, не запускаючи пошук повторно.
- Стани: очікування, пошук, результат, немає підтверджених варіантів, помилка, таймаут, застарілі умови. Ліміт працівника — 8 хв, видимий таймаут — 9 хв. Мережева невизначеність старту не провокує автоматичного повторного витрачання коштів.
- Відбиток наступного пошуку включає попередній вибір та його істотні умови, без рекурсивних службових полів. Зміна транспорту робить залежне житло/місця такими, що потребують перевірки; це бачать і Mini App, і `trip.research` у Telegram.
- Офлайн-копія містить актуальні рішення з позначкою необхідності повторної перевірки. Точний розклад і підтвердження придбаних квитків залишаються окремими записами маршруту/бронювань.
- Для вже створеної подорожі бриф не повертається у статус чернетки. Основний маршрут захищено від розходження з Workflow: дати змінюються через наявне перенесення; інші побажання можна уточнювати. Старі робочі розділи доступні через «Усі деталі подорожі».

## Джерела й підключення провайдерів

Рішення власника: партнерських ключів немає; використовувати наявний пошук і підготувати підключення API. У `providers.mjs` визначено `TripSearchRequest`, `TripSearchResult`, `TripSearchAdapter`, можливості провайдерів і спільну перевірку результату. Реальний транспорт зараз — вебпошук наявного Дослідника; партнерські HTTP-адаптери й секрети ще не підключено.

| Джерело                | Доступ                                                                       | Вартість / наступний крок                                                        |
| ---------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Наявний вебпошук       | Використовується в профілі Дослідника                                        | Наявні витрати моделі/пошуку; нову підписку не оформлено                         |
| Booking.com Demand API | Managed Affiliate Partner, договір, Partner Centre, API token і affiliate ID | Умови конкретного партнерського договору; загальну ціну за запит не підтверджено |
| FlixBus API            | Dynamic integration через Online Distribution                                | Потрібні партнерські умови та доступ; ціну не припускаємо                        |
| Airbnb API             | Окрема API-програма та погоджені scopes                                      | Загального туристичного пошукового доступу для цього проєкту не підтверджено     |

Перевірено за офіційними джерелами 22.10.2026: [Booking prerequisites](https://developers.booking.com/demand/docs/getting-started/prerequisites), [FlixBus dynamic integration](https://www.flixbus.com/company/partners/affiliate-partners), [Airbnb API Terms](https://www.airbnb.com/help/article/3418). Ключі не передаються в Mini App, повідомлення чи git.

Майбутній адаптер підключається на сервері після отримання доступу й з’ясування тарифу. Він повертає той самий обмежений набір пропозицій із HTTPS-джерелом, часом перевірки, параметрами ціни/кількості, скасуванням і невідомими умовами. `provider_quote` дозволяється лише для фактичної відповіді автентифікованого провайдера; вебрезультат цей статус не отримує. Інтерфейс і рішення власника змінювати для нового адаптера не потрібно. Бронювання та платежі не входять у поточний контракт.

## Межі поточної реалізації

Вебпошук може знайти корисні сторінки й підтверджені публічні ціни, але не гарантує вільних місць на майбутні дати. Без підтвердження зберігається `price:null`, а не вигадана оцінка. Юридичні вимоги перевіряються для громадянства, документів та маршруту кожного учасника; загальний чекліст не є підтвердженням права на перетин кордону. Автоматичного бронювання, придбання квитків або визначення фактичної локації немає.

## Перевірка

- Ядро: 6148 тестів, 294 файли. Покриття: statements 87.73%, branches 80.45%, functions 88.13%, lines 90.35%; пороги не знижено.
- Mini App: 496 тестів, 69 файлів, включно з 10 новими сценаріями керованого планування.
- Локальний браузерний прохід через справжній `/api/trips` і SQLite: створення Праги, 29 неповторюваних уточнень, транспорт → житло → два місця, підготовка, власна річ і чекбокс, виїзд, прибуття, відвідане місце, повернення й «удома». 44 зміни, 21 знімок, ширини 320/393/430/900, темна та світла теми; без JS-помилок і горизонтального виходу сторінки.
- У браузерній перевірці результати вебпошуку й створення Workflow замінені локальними синтетичними відповідями. Продакшен-дані, справжній туристичний пошук і реальні Telegram-нагадування цим тестом не перевірялися.

## Публікація

Перед увімкненням нового Mini App потрібні оновлений Brain із профілем `trip-research` та синхронізована інструкція `researcher`. Далі публікуються Worker і Mini App. Якщо Worker з’явиться раніше за новий профіль, запит пошуку покаже відновлювану помилку й потребуватиме повтору після готовності Brain. Це слід урахувати в порядку деплою, зокрема для збірок Cloudflare на push. Нових міграцій і туристичних API-ключів цей випуск не потребує.
