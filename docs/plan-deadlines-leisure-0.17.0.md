# План і надійність дозвілля · 0.17.0

## Стани задач

Виконання та час на внесення звіту — різні речі. `lifecycle` обчислюється однаково ядром, Mini App і запитом асистента з фактичного часу та збережених умов. Внутрішній `status` прийняття залишається сумісним із попередніми записами.

| Стан                    | Умова                                                                    |
| ----------------------- | ------------------------------------------------------------------------ |
| Чернетка                | Ще не прийнята задача                                                    |
| Заплановано             | Початок у майбутньому                                                    |
| Очікує виконання        | Можна починати, підтвердженого прогресу немає                            |
| У процесі               | Власник натиснув початок або записав частину результату                  |
| Виконано вчасно         | Повний результат має фактичний час до строку включно                     |
| Виконано із запізненням | Звичайна задача завершена пізніше                                        |
| Не виконано вчасно      | Строк настав без повного вчасного результату або явно обрано невиконання |
| Не виконано · виняток   | Власник окремо погодив зовнішню виняткову обставину                      |

Відкритий екран оновлює час локально щосекунди з поправкою на серверний годинник, без щосекундних API-запитів. У момент строку стан змінюється навіть без нового запиту чи запису нульового звіту. Відсутність підтвердження не підміняється вигаданим знанням про реальні дії людини. Можна пізніше записати справжній час вчасного виконання. Для задачі «встигнути до» пізній факт зберігається, але не виконує умову своєчасності.

Прийняті умови XP не переписуються: строк зміни стану негайний; чинне вікно звіту визначає момент обліку наслідку. Явне «Не виконав» може підсумувати обіцянку раніше, як і попередня дія `forfeit`.

## Результат, пояснення, виняток

Для задачі з одним результатом — кнопки «Виконав / Не виконав», без числового поля. Числовий обсяг збережено для реальних кількісних цілей. Пояснення (`task-note`) на кшталт «проспав» записує контекст без зміни строку, XP чи винятку. Воно доступне також асистенту через спільне ядро.

Зовнішній виняток має окремий закритий блок, пояснення та явне підтвердження зміни умов. Для помилково вказаного винятку є дія відновлення початкових умов зі збереженням пояснення. Історичні записи власника автоматично не перекласифіковуються.

Виняткове перенесення ручної незавершеної задачі вимагає причини, явного підтвердження та майбутнього строку. Попередній строк, новий строк і причина зберігаються в історії. Спільний результат і бюджет XP залишаються тими самими, повторного заробітку немає. Повертається лише реально списаний наслідок. Календарні блоки та результати з джерела таксі через цю форму не переносяться.

Помічник опису відкритий на початку створення. Основні поля — назва, критерій, день і строк; кількісний обсяг, джерело, напрям та оцінка згорнуті. Підказка відрізняє один кінцевий результат із послідовними кроками від незалежних задач із різними строками. Відповідь моделі не приймає план автоматично.

## Дозвілля

При підтвердженні причини кнопка одразу показує «Зберігаю…» та блокує повторне натискання. Назва дії — «Підтвердити й прибрати». Вікно закривається після підтвердження. Для реакцій протокол 3 повертає коротку квитанцію без очікування перерахунку каталогу. Підтверджена реакція відразу відображається в кеші, потім дані перечитуються. Відвідування й плани зберігають повну відповідь із персональною історією.

«Не на цей тиждень», «Зараз немає бажання» й «Не для нашого спільного виходу» тимчасово приховують варіант. «Не хочу саме цей варіант» та «Уже знайомий варіант» стосуються конкретної картки. Ці причини не створюють негативних ваг жанру, формату або категорії; вибір «уже знайомий» не вигадує факту відвідування чи оцінки. Видимий напис «Ілюстрація» прибрано; обкладинки не змінилися.

Після втрати підтвердження перевірка спочатку читає квитанцію за первинним ID команди (`GET ?commandId=…`). Вона перевіряє відповідність оригінальній дії та не пише нових записів. Якщо квитанції немає, повторюється та сама команда, без нового ID. Перевірка також знаходить застосований запис після обриву між записом і квитанцією. Читання D1 починається з primary session, коли API сесій доступний.

## Діагностика й межі перевірки

Збої запитів дозвілля містять час, HTTP-статус або відсутність відповіді, ID запиту, операцію, фазу, напрям збою, тривалість і номер спроби. Технічні деталі можна розкрити й скопіювати біля відновлення та на сторінці «Система». Локально зберігаються до 25 останніх збоїв поточного сеансу, без авторизації, payload, текстів задач або особистих відгуків. Це локальна діагностика, а не повний централізований журнал усіх функцій. Сервер записує безпечний діагностичний контекст без сирої помилки сховища та особистих даних.

Read-only аудит підтвердив: проблемна ранкова задача мала `excepted`, нуль результату та текст повторного засинання саме як `exceptionReason`; успішної команди приховування концерту в журналі не було. Конкретний обраний власником варіант «Не на цей тиждень» збережено однією стабільною командою; відповідь HTTP 200. Точну причину попереднього збою без HTTP-діагностики встановити не вдалося; нова діагностика потрібна для таких випадків. Тестових production-задач і відвідувань не створено. Міграцій схеми для релізу немає.
