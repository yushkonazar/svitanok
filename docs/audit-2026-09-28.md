## Важливе уточнення про briefing 28 вересня

Ранковий `brief` о 05:00 UTC завершився green, але коректно пропустив
LLM-залежний запуск, бо на той момент GitHub secret `OPENAI_API_KEY` ще був
відсутній. Новий secret додано о 07:54 UTC. Тому публічний status чесно ще
показує briefing за 27 вересня — це не поломка Worker-а.

Першою повною перевіркою нового ключа буде найближчий штатний ранковий
briefing. Не запускати `force=true` лише заради аудиту: він навмисно надсилає
додаткове повідомлення в Telegram. Після штатного запуску `/status` має
показати готовий briefing без згадки про відсутній OpenAI key.

## Виправлення, внесене під час аудиту

`vps-preflight.yml` перевіряв застаріле й заборонене ім'я
`OPENAI_SHADOW_THREAD_IDS`. Чинний brain приймає
`OPENAI_SHADOW_TARGETS`; через стару перевірку звіт міг вводити в оману.

Preflight тепер безпечно показує тільки allowlisted, не секретні verdict-и:
provider, rollout та наявність canary/shadow targets і profiles. Тест
`release-pipeline.test.ts` не дозволить повернути застарілу назву. Жоден
секрет або значення EnvironmentFile в Actions log не виводяться.

## Ризики й план закриття

### P0 — активна аварія

Немає. Поточні ознаки production здорові: Worker, CI, VPS service, `/ready`,
прямі GPT-відповіді та dependency audit.

### P1 — закрити до визнання переходу остаточним

1. **Підтвердити перший штатний briefing після ротації ключа.** Це закриває
   незалежний GitHub Actions шлях, який не перевіряє звичайне повідомлення
   асистенту через VPS. Перевірка: `/status` після ранкового запуску та один
   звичайний GPT-запит у темі «Асистент».
2. **Завершити семиденний GPT-soak і тільки тоді прибирати Claude fallback.**
   Потрібні лише агрегати: немає Claude model steps, немає scheduler rows без
   profile, failure rate за добу <5% при щонайменше 10 model runs. До цього
   не видаляти SDK, OAuth token чи rollback-код.
3. **Інвентаризувати старий `/opt/svitanok-brain/.env` без читання значень.**
   Сервіс уже використовує shared `brain.env`, але старий файл досі доступний
   користувачу brain і може зберігати старі облікові дані. Спершу порівняти
   лише назви ключів і переконатися, що жоден unit/скрипт його не читає;
   видалення або архівація — лише після відкликання старого ключа.
4. **Відділити чинні OpenAI runbook-и від historical Claude матеріалів.**
   `README`, `SPEC`, частина canonical docs і `host/` описують колишній
   Claude-path як бойовий. Це не впливає на запущений GPT brain, але може
   призвести до неправильного аварійного відновлення. Після soak: оновити
   canonical docs, змінити опис пакета brain, прибрати зайві GitHub/VPS
   secrets і залежність Claude SDK одним контрольованим changeset-ом.

### P2 — надійність і спостережуваність

1. **Один release-контур для schema + Worker.** Зараз D1 migration і
   Cloudflare Git deployment — незалежні механізми. У майбутній schema-зміні
   код може вийти раніше за міграцію. Потрібно запровадити compatibility gate
   або контрольований pipeline `migration → deploy → authenticated smoke`.
2. **CI security gate вже додано.** Він запускає `npm audit --omit=dev` для
   root, brain і dashboard та блокує moderate+ production advisory. Dependabot
   #445 не зливати; оновити Cloudflare/Vitest toolchain сумісним пакетом у
   окремій гілці з повним CI.
3. **Дати owner-facing status ідентифікатор build Worker-а.** Зараз публічний
   `/api/status` корисно показує freshness briefing, але не дозволяє
   однозначно зіставити production Worker з commit GitHub. Безпечний
   build-id/commit у захищеному `/status` зробить rollback і перевірку
   deployment детермінованими.

### P3 — hardening без зміни Mini App функцій

1. На `/app/` не видно явних `Content-Security-Policy`,
   `X-Content-Type-Options` і `Referrer-Policy`. Додати їх у Worker після
   окремої compatibility-перевірки Telegram WebView; не змінювати Mini App UI.
2. Вирішити, чи `HEAD /api/status` має відповідати як `GET`. Це не блокує
   користувацький флоу, але спрощує стандартні uptime-probes.

## Обмеження цього аудиту

Відкриту Cloudflare D1 aggregation query не виконано: у цьому сеансі немає
авторизованої Cloudflare browser session, і аудит не створював токен чи не
обходив login. Це не підміна «немає проблеми»: пункт 2 P1 лишається явним
release gate і покривається наявною production soak-автоматизацією.
